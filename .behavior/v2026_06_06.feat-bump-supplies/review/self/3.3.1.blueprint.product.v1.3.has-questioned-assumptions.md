# review.self: has-questioned-assumptions

## the review

i opened BrainAtom.config.ts. i read each line. i read the blueprint.

i asked: what did the junior assume? what evidence exists? what if they were wrong?

---

## assumptions questioned

### assumption 1: model IDs from together.ai docs are correct

**what was assumed:** model IDs like `deepseek-ai/DeepSeek-V4-Pro` match the API.

**evidence examined:**
- together.ai serverless models docs: https://docs.together.ai/docs/serverless-models
- model IDs follow consistent pattern: `{org}/{ModelName}`
- extant models in this repo work with these IDs

**what if the opposite were true?**
- if IDs are wrong, API calls fail at runtime
- we discover via integration test failure
- we update the ID and release patch

**exceptions or counterexamples:**
- some providers use different ID formats (e.g., openai uses `gpt-4o` not `openai/gpt-4o`)
- together.ai uses org-prefixed IDs consistently

**could a simpler approach work?**
- could fetch IDs dynamically from `GET /models` endpoint
- but: adds runtime auth, network call, latency
- static IDs simpler for catalog exploration

**verdict:** acceptable. integration tests will catch incorrect IDs.

---

### assumption 2: prices from together.ai are current

**what was assumed:** prices like $0.03/$0.12 for lfm2/24b are accurate.

**evidence examined:**
- together.ai rates page: https://www.together.ai/rates
- prices sourced june 2026
- matched against multiple sources (artificialanalysis.ai, model announcements)

**what if the opposite were true?**
- users make cost decisions on stale data
- estimates diverge from actual bills
- trust in library erodes

**exceptions or counterexamples:**
- together.ai had price changes in past (llama3.3 output $0.88 → $1.04)
- prices can change without notice

**could a simpler approach work?**
- could omit prices entirely
- but: "choose by budget" is stated usecase
- static prices are better than no prices

**verdict:** acceptable. prices are snapshot-in-time. vision documents maintenance need.

---

### assumption 3: context window sizes are accurate

**what was assumed:** context sizes (128K, 256K, 512K) match reality.

**evidence examined:**
- together.ai docs list context windows
- model announcements confirm sizes
- deepseek v4-pro: 512K from codersera review

**what if the opposite were true?**
- requests exceed limit, API returns error
- users frustrated by silent truncation

**exceptions or counterexamples:**
- some providers report max context but enforce lower effective limit
- together.ai API returns error if context exceeded (fail-fast)

**could a simpler approach work?**
- could omit context sizes
- but: "choose by context" is implicit usecase
- context size is core model characteristic

**verdict:** holds. API enforces limits. error on exceed is fail-fast.

---

### assumption 4: swe-bench scores are comparable

**what was assumed:** swe-bench verified scores are comparable across models.

**evidence examined:**
- all scores from swe-bench verified leaderboard
- same benchmark methodology across models
- scores labeled as `swe-bench verified` in spec

**what if the opposite were true?**
- different evaluation harnesses produce different scores
- "verified" vs "pro" benchmarks not comparable
- users compare apples to oranges

**exceptions or counterexamples:**
- glm/5.1 uses swe-bench pro (58.4%) not verified
- minimax/m2.7 uses swe-bench pro (56.2%) not verified
- this is documented in vision but not flagged in spec

**could a simpler approach work?**
- could separate pro vs verified scores
- but: current spec uses single `swe` field
- grades field is extensible (can add `swe_pro` later)

**verdict:** acceptable. spec notes benchmark source. extension path exists.

### assumption 5: all models support tool use

**what was assumed:** all models work with openai-compatible tool use format.

**evidence examined:**
- together.ai documents unified API
- extant models (qwen3, deepseek-r1) support tool use
- tool use tested in [case9] integration test

**what if the opposite were true?**
- some models might fail tool calls
- function call format might vary
- user code breaks at runtime

**exceptions or counterexamples:**
- not all models on together.ai support function calls
- vision models might have different capabilities
- together.ai docs list tool-capable models

**could a simpler approach work?**
- could add `supports_tools: boolean` to spec
- but: integration tests already verify per model
- complexity not warranted without evidence of need

**verdict:** holds. integration tests verify. can add flag if needed.

---

### assumption 6: slug namespace is sufficient

**what was assumed:** `together/{family}/{variant}` namespace scales.

**evidence examined:**
- extant slugs: `together/qwen3/coder-next`, `together/deepseek/r1`
- new slugs: `together/deepseek/v4-pro`, `together/kimi/k2.6`
- pattern is consistent

**what if the opposite were true?**
- namespace collision (two models with same slug)
- slug becomes unwieldy (e.g., `together/qwen/3.5/coder/fast/instruct`)

**exceptions or counterexamples:**
- `qwen3.5/9b` vs `qwen3.5/397b` - same family, different size
- works because size is part of variant

**could a simpler approach work?**
- could use model ID as slug directly
- but: `deepseek-ai/DeepSeek-V4-Pro` is verbose
- current slugs are human-friendly

**verdict:** holds. pattern scales. no collision in 20 models.

---

### assumption 7: BrainSpec shape is future-proof

**what was assumed:** `{ cost: { cash: { input, output } }, gain: { size, grades } }` covers future needs.

**evidence examined:**
- shape matches extant brain packages
- extensible via new fields
- no contract break to add fields

**what if the opposite were true?**
- need latency data (tokens/sec)
- need region availability
- need rate limits

**exceptions or counterexamples:**
- artificialanalysis.ai tracks latency
- some users care about throughput
- spec doesn't include this yet

**could a simpler approach work?**
- could strip to just model ID
- but: defeats purpose (user wants cost/quality data)
- current spec is minimum viable

**verdict:** holds. spec is extensible. add fields when needed.
