# review.self: has-questioned-assumptions

## the review

i stopped. i opened BrainAtom.config.ts. i read each new entry.

i asked: what did i assume? what if i was wrong?

## assumptions questioned

### assumption 1: model IDs are stable

**the assumption:** model IDs like `deepseek-ai/DeepSeek-V4-Pro` won't change

**what if the opposite were true?**
- together.ai could rename models (v4-pro → v4.1-pro)
- they could deprecate models without notice
- model ID format could change entirely

**evidence for assumption:**
- together.ai docs show stable IDs historically
- deprecation is announced in advance
- openai-compatible format is industry standard

**could a simpler approach work?**
- could fetch model IDs dynamically from API
- but: adds runtime dependency, latency, auth requirement
- static config is simpler for catalog exploration

**verdict:** acceptable. integration tests catch breaks. static config is simpler.

---

### assumption 2: BrainSpec structure is sufficient

**the assumption:** cost/gain structure covers user needs

**what if the opposite were true?**
- users might need latency data (tokens/sec)
- users might need region availability
- users might need rate limits

**evidence for assumption:**
- extant brain packages use same spec
- no feature requests for more data
- spec is extensible (can add fields)

**could a simpler approach work?**
- could strip spec to just model ID
- but: defeats purpose (user wants cost/quality data)
- current spec is minimum for stated usecases

**verdict:** holds. spec covers stated usecases. extensible if needed.

---

### assumption 3: all models use unified API

**the assumption:** all models work with same together.ai chat format

**what if the opposite were true?**
- some models might require different parameters
- tool use format might vary
- output structure might differ

**evidence for assumption:**
- together.ai documents unified openai-compatible API
- integration tests verify each model
- extant models all use same format

**could a simpler approach work?**
- could add per-model config overrides
- but: no evidence needed yet
- unified format is simpler

**verdict:** holds. tests verify. can add overrides if evidence emerges.

---

### assumption 4: static prices are acceptable

**the assumption:** prices hardcoded in config are useful despite staleness risk

**what if the opposite were true?**
- prices change, estimates become wrong
- users make decisions on stale data
- library reputation suffers

**evidence for assumption:**
- together.ai prices change monthly at most
- users can verify live rates on together.ai
- vision documents maintenance need

**could a simpler approach work?**
- could omit prices entirely
- but: "choose by budget" is stated usecase
- static prices better than no prices

**verdict:** acceptable with documented maintenance plan.

---

### assumption 5: swe-bench scores are meaningful

**the assumption:** swe-bench verified scores help users choose models

**what if the opposite were true?**
- swe-bench might not predict real-world performance
- different tasks need different capabilities
- scores could be gamed or unreliable

**evidence for assumption:**
- user asked for "best" models
- swe-bench is industry standard for code
- all scores from verified leaderboard

**could a simpler approach work?**
- could omit grades entirely
- but: "choose by quality" is stated usecase
- swe-bench is best available metric

**verdict:** holds. scores from verified source. best available proxy.

---
