# review.self: has-questioned-deletables

## the pause

i stopped. i read BrainAtom.config.ts line by line.

i asked: for each line i added, would i add it back if deleted?

## hard questions asked

### question 1: do we need ALL 10 new models?

**what if we deleted half?**
- user asked for "fast & cheap" AND "big & best" models
- each tier serves different use case (budget vs quality)
- removal would leave gaps in catalog

**if deleted, would we add back?**
- lfm2/24b ($0.03 input): yes, cheapest option by far
- deepseek/v4-pro (80.6% swe): yes, frontier performer
- minimax/m2.5 (80.2% @ $0.30): yes, best value ratio

**verdict:** all 10 serve distinct purpose. no duplicates.

### question 2: do we need BrainSpec for each model?

**what if we used minimal spec?**
- could store just model ID and description
- cost/gain data would be external

**why we keep full spec:**
- usecase states "choose by budget" - needs cost data inline
- usecase states "choose by quality" - needs grades inline
- full spec enables programmatic model selection

**verdict:** full spec is the product. minimal spec defeats purpose.

### question 3: do we need integration test updates?

**what if we skipped test coverage?**
- unit test verifies catalog has 20 atoms
- integration tests verify each model responds

**why we keep tests:**
- model IDs could be wrong (typo, deprecation)
- api behavior could differ per model
- tests catch these at CI time

**verdict:** integration tests are essential verification.

### question 4: did we over-optimize?

**review of implementation:**
- no abstraction added
- no new files created
- no new patterns introduced
- pure data addition to extant structures

**verdict:** impossible to over-optimize what wasn't optimized.

## conclusion

i questioned each component. asked "would we add it back?"

answer: yes, each piece serves stated usecases.

this is minimum viable: data entries in extant config.
